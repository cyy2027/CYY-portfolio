# 赛博猫狗：四足机器人双平台（01）

> 同一个母题，两套架构各做一遍：**🐕 HyperDog 走「MCU 单机主控 + CAN」**，
> **🐈 Nybble 走「Linux + ROS 2 + micro-ROS 分层」**。
>
> 这不是为了凑数量，而是因为它们回答了同一个问题的两个方向：
> **实时性和算力，到底该把边界划在哪一层？**

## 一、为什么要拆成两套

| 维度 | 🐕 HyperDog 单机 MCU 主控 | 🐈 ROS 2 + micro-ROS 分层 |
|---|---|---|
| 控制节奏 | 主控 1 kHz 下发关节角，200 Hz 步态调度 | 上位机 100 Hz 下发，底层插值平滑 |
| 实时性来源 | MCU 硬实时，不依赖任何网络 | 依赖 Agent + 串口链路，抖动要由底层吸收 |
| 算力上限 | 受 MCU 主频与 RAM 限制 | 上位机不限，可上 numpy / 优化求解 |
| 生态 | 私有 CAN 帧，封闭但可控 | 原生 ROS 2 topic，可直接接导航 / 建图 |
| 断链行为 | 无链路，故障即本地收腿 | 必须显式设计超时降级，否则关节停在原地 |
| 更适合 | 量产、低成本、单机自主 | 研究、算法快速迭代、多机协同 |

一句话结论：**要确定性和成本选左边，要迭代速度和生态选右边；
真正的工程判断是知道什么时候该换边——以及换边后安全逻辑该跟着搬到哪里。**

## 二、两个子项目

### 🐕 [hyperdog_rtos_control](./hyperdog_rtos_control/README.md) — 底层硬核路线

- **架构**：STM32F407 + FreeRTOS + CAN 2.0B 一主多从。主控负责姿态解算、步态相位调度与故障安全，
  4 个关节节点各自下沉 FOC 闭环，算力分层解耦。
- **关键设计**：1 kHz 关节指令下发 · 200 Hz 步态主循环 · 五次多项式足端轨迹 · 自适应互补滤波 ·
  四级故障保护与平滑收腿 · 中断只搬数据不做事。
- **状态**：设计 + 调试复盘文档（本目录 `README.md`）。固件源码与原理图**未纳入本仓库**。

### 🐈 [nybble_micro_ros](./nybble_micro_ros/README.md) — 软件生态路线

- **架构**：Ubuntu + ROS 2 Foxy 规划层 → micro-ROS Agent（XRCE-DDS）→ STM32 + FreeRTOS 执行层，
  UART + DMA 传输，12 路关节角度以 Topic 周期下发。
- **关键设计**：DMA 批量接收 + 环形缓冲 + FreeRTOS 队列三段式消抖 · 上位机带时间戳下发、底层插值 ·
  TIM1/TIM8 原生 PWM 取代 PCA9685 扩展板（省 I²C，时序可控）。
- **状态**：**仅架构设计**（`design.md`），无实机、无自有代码，文档内指标为设计目标值。

## 三、两套方案共用的三条判断

1. **安全逻辑永远放在离电机最近的那一层**。上层可以崩溃、可以断链、可以输出 NaN，
   但收腿动作必须由本地独立完成。
2. **上层下发必须带时间戳，底层必须做插值**。否则 10 ms 一拍的阶跃目标会直接砸进执行器，
   表现为抖动、异响、机械件加速磨损。
3. **通信层要能回答「丢了怎么办」**，而不是「平均时延多少」。平均值好看、p99 崩掉的链路，
   在实机上就是随机翻车。

## 四、关于命名

「赛博猫狗」指的是平台形态：HyperDog 是狗形四足，Nybble 是猫形小型四足（12 自由度舵机关节）。
两者共用同一套分层思想，但**实时边界划在不同位置**——这正是把它们放在同一个编号下对照的意义。
