# 具身智能边缘计算平台（预研方案）

> 🚧 **状态：方案设计阶段** ｜ 0 行代码 ｜ 无硬件 ｜ 无实测数据
>
> 本文是**技术方案与验证路线**，不是已交付项目。文中所有性能数字均为 **目标值（Target）**，
> 未经实测；凡未验证的判断都标注了「待验证」。把它公开的目的是记录问题拆解思路，而不是展示成果。

## 一、为什么记这一笔

已交付的项目里，控制算法跑在 MCU 上（实时但算力有天花板），Linux 侧只做网关与数据转发。
具身智能要求把「感知-决策」搬进机器人本体，而决策侧（RL / MPC 策略推理）天然要跑在带 NPU 的
Linux SoC 上——那是一套**非实时**的系统。于是问题变成：

> **在 RK3588 这类非实时 Linux 与 MCU 实时域之间，能否构造一条延迟可界定的控制通路，
> 使上层策略推理的调度抖动不传导到关节电流环？**

这个预研就是要回答它，并给出可证伪的分阶段验证计划。

## 二、目标系统分层

```text
┌────────────── 训练侧（离线，PC / 服务器） ──────────────┐
│  Isaac Lab / MuJoCo 仿真　域随机化　RL 策略训练           │
└────────────────────────┬────────────────────────────────┘
                         │ 导出策略权重（.onnx → .rknn）
┌────────────────────────▼──── 大脑：RK3588（Linux，非实时） ────────────┐
│  感知：相机 / IMU / 关节反馈 → 状态估计                                 │
│  决策：策略推理（NPU，标称 6 TOPS INT8）                                 │
│  输出：关节目标角 / 前馈力矩　@ 50 Hz（目标端到端 < 20 ms）              │
└────────────────────────┬────────────────────────────────────────────────┘
                         │ 异构链路（选型未定：CAN FD / EtherCAT / SPI+共享内存）
┌────────────────────────▼──── 小脑：MCU 实时域（RTOS） ─────────────────┐
│  指令插值与限幅 → 逆运动学 → 关节 FOC 电流环 @ 20 kHz                    │
│  安全兜底：通信超时降级、看门狗、平滑收腿（**不依赖上层存活**）           │
└────────────────────────┬────────────────────────────────────────────────┘
                         │ CAN / PWM
                    执行器（关节模组）
```

关键设计约束（这三条是架构的地基，不是实现细节）：

1. **安全边界必须在实时域内闭合**。上层 Linux 崩溃、策略输出 NaN、通信中断，机器人都要能自己
   平稳收腿停下，不依赖任何来自大脑的指令。
2. **两域时间尺度差 3 个数量级**（50 Hz 决策 vs 20 kHz 电流环）。中间必须有一层插值/限幅，
   不能让 20 ms 一拍的阶跃目标直接砸进电流环。
3. **延迟要可测量、可分解**。把「感知→推理→传输→插值→电流环」每一段单独打点，否则调不动。

## 三、四个核心问题（按风险从高到低）

| # | 问题 | 难点在哪 | 打算怎么验证 |
|---|---|---|---|
| 1 | **时间尺度错配** | 策略 50 Hz 输出的是「20 ms 后该到哪」，电流环要 20 kHz 连续可导的目标 | 在 MCU 侧做五次多项式/临界阻尼插值，用阶跃与正弦跟踪测相位滞后与超调 |
| 2 | **通信确定性** | CAN FD 在 1 Mbit 仲裁段下，标准帧最坏排队时延随负载非线性上升；抖动比平均时延更致命 | 满负载打流 30 min，统计单向时延的 **p99 与最大值**，而非平均值 |
| 3 | **Linux 侧非实时** | 普通内核调度抖动可达毫秒级，PREEMPT_RT 也只是「更小」而非「有界」 | 用 cyclictest 记录 max latency 分布；对比「双域」与「单 Linux 域」两种方案的抖动传递 |
| 4 | **Sim-to-Real 差距** | 仿真里的接触模型、执行器延迟、传感器噪声都与实机不同，策略迁移后性能断崖 | 域随机化参数表 + 逐项消融，记录每项随机化对实机成功率的影响 |

## 四、分阶段路线与验收口

每个阶段都设「不达标就退回上一阶段」的判定，避免一路堆到实机才发现地基是空的。

| 阶段 | 内容 | 验收指标（Target） | 失败退路 |
|---|---|---|---|
| **P0** 单板 Bring-up | RK3588 刷系统、串口/网口、NPU 工具链（RKNN-Toolkit2）跑通官方 demo | 推理 demo 跑通；记录单帧推理基线时延 | 换板卡或降级为纯 CPU 推理先跑通链路 |
| **P1** 实时域独立闭环 | MCU 上单关节 FOC 电流环 + 编码器，独立于 Linux 运行 | 电流环 20 kHz；阶跃响应超调 < 5%，调节时间 < 10 ms | 退回 03 项目已验证的电压模式 FOC 方案 |
| **P2** 异构链路打通 | 选型定案并实现双向通信 + 超时降级 | 单向时延 p99 < 1 ms；人为断链后 100 ms 内进入安全收腿 | 降级到 CAN 2.0B（1 Mbit）并放宽指标 |
| **P3** 策略端侧推理 | 一个**简单**策略（如 MLP 平衡/站立）部署到 NPU，闭环跑 | 单帧 < 2 ms；50 Hz 闭环连续 30 min 不丢帧、不漂移 | 先用 MPC/CPG 传统方法验证链路，策略延后 |
| **P4** Sim-to-Real | 仿真训练 → 实机迁移，做域随机化消融 | 定义清楚「成功率衰减」并量化，而不是只说"能走" | 缩小任务域（先原地站立/抗扰，再行走） |

> 阶段顺序刻意把「链路」放在「策略」之前：策略能不能跑是算法问题，链路通不通是工程问题，
> 后者不通的时候，前者的一切调参都是白费。

## 五、选型权衡（含否决理由）

| 决策点 | 候选 | 倾向 | 理由 |
|---|---|---|---|
| 实时域组织方式 | ① 单 Linux + PREEMPT_RT ② 双域（Linux + MCU） ③ Linux + EtherCAT 从站 | **②** | 只有 ② 能让安全逻辑独立于 Linux 存活；①的抖动无上界，③成本与复杂度对单机预研过重 |
| 异构链路 | CAN FD / EtherCAT / SPI+共享内存 | **CAN FD（待验证）** | 复用 01 项目已跑通的 CAN 主从架构与故障安全经验；EtherCAT 留作 P2 若 p99 不达标的后手 |
| 算力平台 | RK3588 / Jetson Orin Nano | **RK3588** | 手头生态与成本更可控，6 TOPS INT8 对 MLP/小 CNN 策略够用；Orin 的 CUDA 生态优势在本阶段用不上 |
| 双足 vs 四足验证平台 | Qmini 双足 / 自建四足（复用 01） | **先用四足** | 四足侧已有 CAN 主控与步态积累，可控变量更少；双足作为 P4 之后的迁移目标 |

## 六、与已有项目的关系（为什么这不是空想）

| 本方案需要的模块 | 已有前置 |
|---|---|
| 小脑侧多关节 CAN 主从、1 kHz 指令下发、分级故障安全 | **01 HyperDog 主控固件**（已跑通） |
| 单关节 FOC 电流环、编码器反馈 | **03 STM32 无刷电机 FOC**（电压模式，无电流采样） |
| Linux 侧部署、Socket 跨域通信、断线重连与本地缓存 | **05 工业物联网边缘网关**（RK3568） |
| 实时任务划分与优先级设计 | 01 / 04 / 07 的 FreeRTOS 工程实践 |

也就是说，这条路线的每一层都有一个**已经交付过的项目垫底**，缺的是把它们接起来、并把时间尺度
对齐这一环。这是我认为它值得立项的理由。
