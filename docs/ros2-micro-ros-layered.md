# ROS 2 + micro-ROS 分层控制：把实时边界从板内挪到链路上

> 📄 文档路径：`docs/ros2-micro-ros-layered.md`

> ✍️ 分层控制的典型诱惑是"规划全放上位机，MCU 只当执行器"。听起来清爽，实际代价是**实时边界从板内退到了链路上**——一半的工程量变成治理抖动与丢包。本文讲清这条链路的架构、XRCE-DDS 的取舍、三段式接收的实现，以及什么时候该退回单机方案。

> ⚠️ **文档定位**：对应 [nybble_micro_ros](../personal_project/01_quadruped_robotics/nybble_micro_ros) 的架构设计（12 自由度舵机四足，ROS 2 Foxy + XRCE-DDS + STM32）。**无实机、无自有代码**，本文是设计推演与通用工程要点，性能数字为设计目标。整套方案的上层动机见[《大脑—小脑异构架构》](./embodied-brain-body-arch.md)。

---

## 一、为什么要 micro-ROS

ROS 2 底层是 DDS。DDS 的发现机制、QoS 协商、序列化开销，对一颗几百 KB RAM 的 MCU 来说是不可能承受的：

| 项 | 原生 DDS（Linux） | micro-ROS（MCU 侧） |
|---|---|---|
| 代码体积 | 数 MB | 几十～上百 KB |
| 动态内存 | 大量堆分配 | 静态分配 + 预置缓冲池 |
| 发现机制 | 组播自动发现 | 由 Agent 代理，Client 只连一个端点 |
| 传输 | UDP / 共享内存 | 串口 / UDP / CAN，可裁剪 |

关键在 **XRCE-DDS 的 Client–Agent 模型**：

```text
┌─────────────── Linux 上位机 ───────────────┐        ┌──────── MCU ────────┐
│  ROS 2 节点（IK / 步态 / 姿态补偿）         │        │  XRCE-DDS Client    │
│        ▲                                   │        │        ▲            │
│        │ DDS（本地，全功能）                  │        │        │ 精简协议   │
│  ┌─────┴──────────┐                        │  UART  │  ┌─────┴─────────┐  │
│  │ micro-ROS Agent │◄───────────────────────┼────────┼──┤ 应用任务       │  │
│  └────────────────┘   序列化后的 XRCE 帧     │        │  └───────────────┘  │
└────────────────────────────────────────────┘        └─────────────────────┘
```

Agent 在 Linux 侧充当"翻译"：对上是一个正常的 ROS 2 节点，对下用极简协议跟 MCU 通信。MCU 侧只需要实现 Client 状态机 —— 发布/订阅在协议层就是"注册 DataWriter / DataReader"，不用实现发现。

**这个模型的代价**：所有 Topic 数据都要过一次 Agent 的序列化往返，且 Agent 是单点。Agent 卡住，MCU 和 ROS 2 就断联 —— 而 Agent 跑在非实时域里。

## 二、实时边界退化的三层后果

单机方案里，从"算目标角"到"出 PWM"是同一个 MCU 内的函数调用，延迟是确定的。分层之后中间插了两跳，每一跳都带来新的不确定性：

| 环节 | 不确定性来源 | 量级（经验） |
|---|---|---|
| 上位机节点调度 | 非实时 Linux，Python 节点还要过 GIL | 毫秒级抖动 |
| Agent 序列化 + 传输 | 缓冲队列、UART 波特率、驱动中断 | 亚毫秒～数毫秒 |
| MCU 接收 | 串口中断密度、任务优先级 | 微秒～毫秒 |

结论不是"不能做"，而是：**MCU 侧必须有能力吸收这些抖动**，否则上位机的每一点调度毛刺都会变成关节的电流尖峰。

吸收抖动的三件套：**缓冲区 + 时间戳 + 插值**。缺一个都不行。

---

## 三、三段式接收：中断只搬数据

最反直觉的一条：**不要在串口中断里解析协议**。

串口在 1 Mbaud 下，每个字节约 10 µs 到达。一帧 100 字节，中断要进来 100 次。如果每次都在中断里做状态机解析并写队列，中断占用会挤占电机控制任务 —— 在 200 Hz 步态循环下，这种挤占表现为**步态相位抖动**，且极难定位（因为逻辑没错，只是时间不对）。

三段式：

```text
UART DMA（循环模式）
    │  硬件把字节搬进环形缓冲，CPU 不参与
    ▼
环形缓冲区（ring buffer）
    │  生产者：DMA（无锁，只写 head）
    │  消费者：解析任务
    ▼
FreeRTOS 队列 / 流缓冲
    │  完整帧入队
    ▼
ros_msg_recv_task  ──► 指令解析 ──► 目标角写入共享结构
```

要点：

1. **DMA 用循环（circular）模式**，不是单次。单次模式每帧都要重启，中断次数反而更多。
2. **环形缓冲用"读写下标 + 内存屏障"实现无锁**。单生产者单消费者场景不需要关中断。
3. **解析任务优先级要低于电机控制任务，但要高于状态上报**。太低会被饿死，太高会抢占控制。
4. **缓冲区留余量**。按最坏情况算：最大帧长 × 允许积压帧数。余量不足时宁可丢最旧的帧，不要阻塞生产者。

## 四、时间戳 + 插值：把"周期性到达但带抖动"还原成连续运动

上位机固定 100 Hz 下发目标角，实际到达时刻会有 ±几毫秒的抖动。如果 MCU 收到就立刻执行，等于把抖动原样转成速度突变。

正确做法：

```text
帧结构： [seq][timestamp_us][joint_targets...]

MCU 侧：
  收到帧 → 入队（按 timestamp 排序）
  控制周期到（1 kHz）→
      取队首两帧 → 按本地时钟插值 → 输出目标角
      若队首帧时间已过 → 出队，取下一帧
```

三个细节：

- **时间戳用上位机的 `CLOCK_MONOTONIC`，MCU 侧做一次偏移标定**（开机时连续采若干帧，取最小单向延迟作为偏移）。
- **插值用匀速（线性）就够**，因为 100 Hz 下相邻帧间隔 10 ms，线性误差可以忽略；用五次多项式反而引入额外计算。
- **欠载策略**：若队列空了（上位机掉帧），保持最后一个目标角并**缓慢向当前位置收敛**，而不是继续外推 —— 外推在丢帧时会造成过冲。同时置一个"链路异常"标志给安全逻辑。

## 五、QoS：别用默认值

ROS 2 的默认 QoS 是 `RELIABLE` + `KEEP_LAST(10)`。对控制指令流，这个默认值有三个问题：

| QoS 维度 | 默认 | 控制流应该选 | 理由 |
|---|---|---|---|
| Reliability | RELIABLE | **BEST_EFFORT** | 旧指令重传没有意义，迟到的指令比丢掉的更危险 |
| History / Depth | KEEP_LAST 10 | KEEP_LAST 1～2 | 积压的旧指令必须被丢，不能排队执行 |
| Durability | VOLATILE | VOLATILE | 新订阅者不需要历史指令 |

**RELIABLE 在链路拥塞时会触发重传，导致延迟雪崩**：重传的旧帧占满带宽，新帧更迟到，越堵越糟。控制指令是"最新有效"，不是"全部送达"——这个语义差异用 BEST_EFFORT 表达才对。

状态回传（MCU→上位机）则相反：可以 RELIABLE，因为关节角序列丢失会影响状态估计。

## 六、什么时候该退回单机方案

这是本文最实用的部分。分层不是默认更优，它有明确的适用边界：

| 判断依据 | 选分层（ROS 2 + micro-ROS） | 选单机（MCU 全包） |
|---|---|---|
| 算法迭代频率 | 高（步态天天改） | 低（参数固化） |
| 算力需求 | 需要矩阵运算 / 视觉 / 学习策略 | 纯解析式，MCU 富余 |
| 硬件成本 | 能接受上位机 | 成本敏感 |
| 实时确定性要求 | 中等（能容忍几 ms 抖动） | 高（要求 μs 级确定） |
| 团队协作 | 多人分别做算法与固件 | 单人 |
| 产品形态 | 研究平台 / 原型 | 量产设备 |

一个反直觉的结论：**量产往往退回单机**。因为量产的算法已经固化，不需要天天改；而每台设备多一块 Linux 板，BOM 和故障率都不划算。分层方案的价值集中在研发阶段。

## 七、失败模式

| 现象 | 根因 | 排查方向 |
|---|---|---|
| 步态相位周期性抖动 | 串口中断抢占控制任务 | 改 DMA + 三段式；看中断耗时 |
| 偶发大幅动作 | 队列积压旧指令被执行 | QoS 改 KEEP_LAST 1；插值按时间戳丢弃过期帧 |
| 走几分钟后逐渐变慢/变形 | 时间戳偏移漂移 | 定期重标定时钟偏移 |
| 上位机负载一高就抖 | 节点与 Agent 争 CPU | 绑核；Agent 提优先级 |
| Agent 挂了机器人还在动 | 无心跳检测 | MCU 侧加超时降级 |
| 低速正常、加速丢步 | 链路带宽不足（帧率×帧长 > 波特率利用率 60%） | 降帧率或提速波特率；压缩帧长 |
