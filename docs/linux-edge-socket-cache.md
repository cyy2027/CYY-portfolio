## 概述
在Linux边缘网关设备中，Socket TCP通信为流式协议，不存在数据包边界，极易出现粘包、分包问题。同时边缘网络不稳定，存在网络抖动、断网重连、消息积压场景。
本文基于epoll事件驱动模型，设计一套带收发环形缓存的Socket框架，解决TCP流解析、断连缓冲、流量削峰，适用于边缘网关、物联网采集终端。

## 一、TCP粘包分包原理
TCP是面向字节流的协议，内核不维护应用层数据包边界。
1. 发送端：多个小包被TCP内核合并发送 → **粘包**
2. 接收端：一个大包被内核分片多次返回 → **分包**
> 核心结论：**不能单次recv当作一条完整报文，必须在应用层做帧解析**。

## 二、非阻塞Socket基础配置
```c
// 设置socket为非阻塞
int set_nonblock(int fd)
{
    int flags = fcntl(fd, F_GETFL, 0);
    fcntl(fd, F_SETFL, flags | O_NONBLOCK);
    return 0;
}
```
非阻塞recv/send特性：缓冲区无数据时立刻返回`-1`，errno为`EAGAIN / EWOULDBLOCK`，不阻塞线程。

## 三、收发环形缓存架构
- **接收缓存**：epoll触发可读事件 → recv读取字节写入ringbuf；业务线程从ringbuf读取字节，状态机解析完整帧。
- **发送缓存**：业务生成报文，写入发送ringbuf；epoll可写事件触发时，从ringbuf取出数据调用send。
> 目的：业务逻辑不阻塞IO读写，网络慢时报文暂存缓存削峰。

### 接收流程
1. epoll监测socket可读事件
2. 循环recv，数据写入接收ringbuf
3. 状态机持续从ringbuf取出字节，查找帧头、帧尾、校验
4. 解析成功，将完整报文投递业务队列

### 发送流程
1. 业务报文写入发送ringbuf
2. 注册epoll可写事件
3. 可写事件触发，从ringbuf取出数据send
4. send发送不完，保留剩余数据，等待下一次可写事件

## 四、epoll LT与ET选型
- LT水平触发（默认）：只要缓冲区有数据，就持续上报事件，编程简单，推荐边缘设备使用。
- ET边沿触发：仅状态变化时触发，必须一次性读完缓冲区全部数据，性能更高，但容易丢数据。
> 边缘网关项目优先LT，降低稳定性风险。

## 五、断网重连缓存策略
1. 网络断开：不再丢弃待发送报文，存入发送环形缓存。
2. 缓存上限：设置最大缓存字节，超过上限丢弃最早消息，防止OOM。
3. 网络恢复：自动重连成功后，按顺序补发缓存报文。
4. 消息可选增加时间戳，长期积压的过期报文直接丢弃。

## 六、工程踩坑记录
1. recv只读取一次就退出，缓冲区残留字节造成报文错乱。
> 解决：非阻塞模式下循环recv直到返回EAGAIN。
2. 发送缓存无限增长，弱网下内存持续上涨触发OOM杀死进程。
> 解决：设置ringbuf最大容量，超出做限流/丢弃旧包。
3. ET模式没有读完缓冲区全部数据，后续不再触发可读事件，永久卡住。
> 解决：边缘设备尽量使用LT；坚持ET则必须循环读至EAGAIN。
4. socket关闭后没有移除epoll监听，产生野文件描述符，epoll返回未知事件崩溃。
> 解决：close前调用epoll_ctl(EPOLL_CTL_DEL)删除fd。
5. 多线程同时读写ringbuf，缺少互斥锁，缓冲区指针错乱。
> 解决：ringbuf读写位置修改加pthread_mutex临界区保护。
6. send返回部分发送，没有保存剩余数据，报文截断损坏。
> 解决：记录已发送偏移，剩余数据留在发送缓存等待下次可写。
