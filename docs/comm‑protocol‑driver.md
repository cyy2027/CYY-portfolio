# Modbus‑RTU + COBS/CRC协议栈设计与踩坑
> 📄 文档路径：`docs/comm‑protocol‑driver.md`
> 
> ✍️ 个人实践总结：嵌入式底层通信驱动与上层协议封装；包含UART/I2C/SPI硬件驱动要点、RS485硬件注意事项、Modbus‑RTU主从机实现、COBS帧封装、CRC校验，记录总线调试、帧粘包、总线冲突等工程实战问题，提供伪代码与排错思路。

## 概述
嵌入式项目中，UART、I2C、SPI是最基础片上外设；在工业场景，常基于串口扩展RS485总线，运行Modbus‑RTU实现多设备组网。
裸机下直接操作寄存器容易出现：丢字节、粘包、帧解析错乱、总线冲突；很多项目把接收处理写在串口中断内部，中断臃肿、业务逻辑侵入底层，后期维护困难。

本文分为**硬件驱动层**和**应用协议层**两部分：底层讲UART/I2C/SPI/RS485驱动设计要点；上层实现Modbus‑RTU主从逻辑、COBS无分隔符帧封装、CRC校验；总结总线现场调试高频故障，给出可复用框架思路。

### 覆盖能力
- UART串口驱动设计：环形缓冲区、半中断接收，解决粘包、断包
- RS485硬件收发控制、总线偏置电阻、总线冲突问题
- I2C、SPI外设驱动常见坑点（时序、超时、信号噪声）
- Modbus‑RTU协议：功能码解析、主站请求、从站应答、帧超时判断
- COBS编码 + CRC16校验：自定义数据包封装，避免0x00分隔符干扰
- 帧解析状态机、超时保护、异常报文过滤
- 实际调试踩坑：丢包、乱码、从站不应答、总线死机

## 一、底层通信外设驱动设计
### 1.1 UART串口：环形FIFO缓冲区
> ❌ 错误做法：在串口接收中断里面直接解析协议、执行业务函数。中断应当只做数据搬运，**业务逻辑放到主循环处理**。

采用“中断接收+环形缓冲区FIFO”架构：
1. USART接收中断：收到1字节，写入接收环形buffer，直接退出中断，不做解析；
2. 主循环轮询：从环形缓冲区取出字节，交给协议解析状态机；
3. 发送：支持阻塞发送 / DMA非阻塞发送。

```c
//环形接收缓冲区结构体
typedef struct{
    uint8_t *buf;
    uint16_t size;
    uint16_t wr;
    uint16_t rd;
}ring_buf_t;

// 判断缓冲区是否有可读字节
static inline bool ringbuf_has_data(ring_buf_t *rb)
{
    return rb->wr != rb->rd;
}

// 从FIFO读取1字节
bool ringbuf_read(ring_buf_t *rb,uint8_t *ch);
// 写入1字节到FIFO
bool ringbuf_write(ring_buf_t *rb,uint8_t ch);
```

> 💡关键要点
- 中断只调用`ringbuf_write()`，禁止复杂运算；
- 缓冲区大小根据业务选型：Modbus‑RTU 建议≥256 字节；
- 缓冲区满需要做丢弃处理，防止数组越界。

### 1.2 RS485 半双工总线要点

RS485 是半双工，**DE/RE 引脚同时控制收发模式**：

- DE=1：发送模式；DE=0：接收模式。
//发送数据前拉高DE，发送完成后延时再拉低DE
void rs485_send(uint8_t *data,uint16_t len)
{
    HAL_GPIO_WritePin(RS485_DE_GPIO_Port,RS485_DE_Pin,GPIO_PIN_SET);
    uart_send_buf(data,len);
    //等待发送寄存器全部移位完成
    while(__HAL_UART_GET_FLAG(&huart1,UART_FLAG_TXE)==RESET);
    while(__HAL_UART_GET_FLAG(&huart1,UART_FLAG_TC)==RESET);
    HAL_GPIO_WritePin(RS485_DE_GPIO_Port,RS485_DE_Pin,GPIO_PIN_RESET);
}
> ⚠️硬件 & 软件踩坑

1. A/B 线必须并联终端电阻 120Ω（总线两端），减少信号反射；
2. 总线增加偏置上 / 下拉电阻，空闲时抑制差分噪声，避免乱码；
3. **绝对不能多个节点同时发送，必须主站轮询，从站被动应答**；
4. 发送完成一定要等待`TC`发送完成标志，不能发送完立刻拉低 DE，会截断最后几个字节；
5. 布线远离继电器、电源功率走线，防止共模干扰。

### 1.3 I2C 驱动常见问题

1. I2C 属于开漏输出，必须外部上拉；没有上拉会通信完全不稳定；
2. 增加通信超时，防止从站卡死把 SCL/SDA 拉低，主程序死等；
3. 不要在高频中断里面调用 I2C 读写；
4. 多设备注意 I2C 地址冲突。

### 1.4 SPI 驱动常见问题

1. CPOL/CPHA 时钟极性相位必须严格和外设器件手册匹配；参数错直接全乱码；
2. NSS 片选：每次读写前拉低，结束拉高；
3. 高速 SPI 注意 PCB 布线，时钟线尽量短。

## 二、自定义数据包：COBS + CRC16 校验

普通串口协议常使用`0x00`作为帧分隔符；如果业务数据本身出现`0x00`，就会发生**帧误分割**。
**COBS(Consistent Overhead Byte Stuffing)**：把帧内部 0x00 全部转义，帧可以统一使用 0x00 作为帧结束标记。
帧格式：`[COBS编码数据][CRC16‑High][CRC16‑Low][0x00帧结束符]`

处理流程：

1. 上层业务 payload，计算 CRC16 校验，追加到负载尾部；
2. 对 payload+CRC 做 COBS 编码；
3. 尾部追加 0x00，通过串口发送；
4. 接收端：不断接收字节，遇到`0x00`代表一帧结束；执行 COBS 解码；校验 CRC；CRC 正确才上交上层业务。

> 
> 💡优势：

- 业务数据任意字节，包含 0x00 也不会破坏帧边界；
- CRC 保证数据完整性，检测传输干扰、字节翻转；

> 
> 解析逻辑伪代码：

```
循环从ringbuf取字节
    if 读到字节 == 0x00:
        结束当前帧；执行COBS解码；校验CRC16；
        CRC正确 → 上交业务层；CRC错误 → 丢弃本帧
        清空临时接收缓存
    else:
        字节存入临时帧缓存
```

## 三、Modbus‑RTU 协议实现要点

Modbus‑RTU 依靠**3.5 字符间隔时间**作为帧结束判断，没有特殊分隔符。
帧格式：`从站地址 + 功能码 + 数据域 + CRC16(低字节在前)`

### 关键时间规则

- 两帧之间间隔 >=3.5 字符时间，判定一帧接收完毕；
- 波特率 9600，3.5 字符约 4ms；115200 约 350us；

> 
> 裸机实现：串口收到字节后，刷新帧接收超时计时器；超时到达代表本帧接收完成。

### 3.1 Modbus‑RTU 从站实现思路

1. 串口环形 buffer 接收字节；
2. 每收到字节重置帧超时计时器；超时触发，把完整报文交给 Modbus 解析；
3. 解析：匹配本机从站地址；校验 CRC16；
4. 根据功能码（03 读保持寄存器、06 写单个寄存器、16 写多寄存器）执行读写；
5. 组装应答帧，RS485 发送应答；异常返回异常码。

### 3.2 Modbus‑RTU 主站实现思路

- 主站主动发起请求，发送之后开启应答超时定时器；
- 等待从站应答；超时没有收到应答，判定从站无响应，进行重传（限制最大重传次数，防止总线风暴）；
- 主站轮询模式：**必须等待上一次应答完成 / 超时，才可以发起下一次请求**，禁止并发多发请求。

> 
> ⚠️禁止：多任务同时调用 Modbus 发送函数，会造成报文错乱，建议增加互斥锁 / 状态机保护。

## 四、帧解析状态机设计

串口通信不要用简单数组缓存，推荐使用解析状态机处理，同时兼容 Modbus‑RTU 和 COBS 自定义协议。
状态枚举示例：

```
typedef enum{
    PARSE_STATE_IDLE,        //空闲，等待帧起始
    PARSE_STATE_RECV_DATA,   //接收帧数据
    PARSE_STATE_FRAME_DONE,  //帧接收完成
    PARSE_STATE_ERROR        //帧错误，丢弃
}parse_state_t;
```

## 五、工程实测踩坑记录

1. **RS485 乱码，空闲总线大量噪声字节**
   - 现象：没有发送的时候，串口不断收到乱码。
   - 根因：总线缺少偏置电阻，差分总线悬浮，耦合干扰。
   - 解决：A 线上拉，B 线下拉，总线两端 120Ω 终端电阻。
2. Modbus 从站应答报文被截断，最后几个字节丢失
   - 现象：抓包看到应答报文不完整，CRC 校验全部失败。
   - 根因：发送完数据立刻拉低 DE/RE，发送移位还没完成。
   - 解决：等待 UART `TC`传输完成标志，再切换收发引脚。
3. **粘包、多帧合并在一起**
   - 现象：一次收到两帧拼接在一起。
   - 根因：DMA / 中断接收速度快，上层处理不及时；
   - 解决：依靠协议本身帧结束条件（Modbus 3.5 字符超时 / COBS 的 0x00 结束符）做帧分割，不要固定长度截取。
4. **Modbus 主站轮询死机，总线不再通信**
   - 现象：某个从站断电，整个总线停止轮询。
   - 根因：没有应答超时机制，程序一直等待从站应答。
   - 解决：每次请求开启超时计时器，超时直接释放总线，进入下一轮轮询；设置最大重传次数。
5. I2C 偶发通信卡死，程序挂死在 I2C 等待循环
   - 现象：概率性卡死，重启恢复。
   - 根因：从设备把 SCL/SDA 拉低，主循环无限 while 等待。
   - 解决：I2C 读写全部增加软件超时计数，超时直接退出，复位 I2C 外设。
6. COBS 解码校验 CRC 经常报错，现场干扰下丢包率高
   - 根因：没有做帧长度限制，噪声随机产生 0x00，产生伪帧。
   - 解决：增加最大帧长校验；小于最小帧长的报文直接丢弃。
7. 多任务并发调用串口发送，报文穿插错乱
   - 现象：发送出来数据包 A 和 B 字节互相穿插。
   - 根因：多个任务同时操作串口发送，没有互斥保护。
   - 解决：信号量 / 互斥锁保护发送接口；或者把所有发送提交到单独发送任务队列。

## 六、总结

1. 底层通信驱动遵循原则：**中断只搬运字节，解析、业务逻辑全部交给主循环 / 任务，中断保持短小快速**。
2. RS485 半双工重点：DE/RE 时序、终端电阻、总线偏置，很多通信问题不是软件 bug，是硬件信号完整性问题。
3. Modbus‑RTU 依靠时间间隔分割帧，一定要做好接收超时检测；主站轮询务必增加应答超时、重传限制。
4. COBS+CRC 适合自定义私有串口协议，解决 0x00 数据干扰帧边界，CRC 保证传输可靠性。
5. 所有外部总线 (I2C/SPI/UART‑485)，全部要增加超时保护，防止外部器件异常把主程序卡死。
6. 多任务环境，发送接口需要互斥保护，避免多帧报文字节互相穿插。
