## 概述
MQTT是物联网最主流的轻量发布订阅协议，适合低带宽、不稳定网络环境的嵌入式终端。MQTT基于TCP，虽然TCP保证字节可靠传输，但MQTT自身QoS、会话、心跳机制才是设备断网恢复后消息可靠的关键。
本文梳理MQTT核心概念、客户端开发要点、消息可靠性设计，覆盖裸机/FreeRTOS ESP32与Linux边缘网关两种场景。

## 一、MQTT基础核心概念
1. **发布订阅模型**：客户端不直接点对点通信，所有消息经过Broker（服务端）转发。发布者发布Topic，订阅者订阅Topic接收消息。
2. **QoS服务质量**
    - QoS0：最多一次，消息发出去即完成，不确认；适合传感器高频非关键数据。
    - QoS1：至少一次，Broker收到消息回复PUBACK；**存在消息重复**，业务层需要做去重。
    - QoS2：恰好一次，四次握手，开销最大；适合支付、控制指令等绝对不能重复场景。
> 工程最常用组合：上报传感器QoS0，设备控制指令QoS1。
3. **KeepAlive心跳**：客户端周期性发送PINGREQ，告诉Broker设备在线；超过2倍keepalive时间无心跳，Broker判定设备离线。
4. **CleanSession**
    - CleanSession=1：连接成功后清除历史会话，离线消息全部丢弃。
    - CleanSession=0：持久会话，Broker保存离线期间发给该客户端的QoS1/QoS2消息，重连后补发。

## 二、特殊消息类型
1. **遗嘱消息 Will**：设备异常掉线（断电、断网）时，Broker自动向指定Topic推送预设遗嘱消息。正常调用disconnect主动下线则不发送。常用于设备在线状态监测。
2. **保留消息 Retained**：Broker保存该Topic最后一条保留消息，新客户端订阅该Topic会立刻收到这条消息，适合设备参数、版本静态信息。
> 注意：发送空payload的保留消息，用于清除Broker上的保留消息。

## 三、客户端开发要点
### 3.1 自动重连框架
1. TCP断连 → MQTT客户端状态置为断开，停止发布消息。
2. 延时退避重连（指数退避，防止短时间大量重试压垮Broker）。
3. TCP连接成功后，发送MQTT CONNECT报文，完成登录。
4. 连接成功回调中，重新执行订阅操作。

### 3.2 消息处理框架
底层TCP使用环形缓冲区接收字节流；上层状态机解析MQTT固定头、剩余长度、可变头与payload。
```c
// MQTT报文固定头（简化）
typedef struct {
    uint8_t msg_type_qos;
    uint32_t remain_len;
} mqtt_fixed_header_t;
```
- 接收：TCP收到字节写入ringbuf，状态机循环解析完整MQTT报文。
- 发送：待发布消息放入发送缓存，网络恢复后依次发送。

## 四、工程踩坑记录
1. Keepalive设置过小，网络轻微抖动就被Broker判定离线，频繁重连。
> 解决：keepalive建议设置30~120s；客户端在小于keepalive/2时间发送心跳。
2. CleanSession=0，但ClientID固定，多台设备共用同一个ClientID，设备被互踢下线。
> 解决：每台设备使用唯一ClientID。
3. QoS1消息只依赖协议层，业务未做去重，控制指令重复执行。
> 解决：消息携带seq序列号，业务层判断序列号，过滤重复报文。
4. 消息发送速率大于网络吞吐，发送缓存无限堆积，内存持续上涨OOM。
> 解决：设置缓存上限，超过阈值丢弃低优先级上报数据。
5. 订阅Topic使用`#`多级通配符放在非末尾位置，协议非法导致订阅失败。
> 规则：`#`只能放在主题最后一级；`+`只能匹配单一级主题。
6. 网络恢复瞬间大量离线消息一次性下发，CPU瞬间被占满，丢失心跳，再次掉线。
> 解决：Broker侧限制离线消息数量；客户端限流消费报文。
7. 遗嘱消息只有异常断网触发，正常disconnect不会发送，不能当成设备正常离线上报。
