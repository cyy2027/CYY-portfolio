
# 量产固件的OTA方案：双分区+CRC+断电回滚

> 📄 文档路径：`docs/firmware‑mass‑produce.md`

> ✍️ 个人实践总结：面向MCU量产固件可靠性设计，包含Bootloader、A/B双分区OTA、完整性校验、看门狗故障恢复、国产MCU迁移适配，记录实际踩坑与解决方案。

## 概述
普通调试版本固件只关注业务功能实现；**量产固件必须解决异常复位、升级断电变砖、程序跑飞、供应链芯片替换**等工程问题。

本文基于 STM32 Cortex‑M 系列 MCU，实现一套可落地的固件可靠性方案：包含 Bootloader 启动管理、A/B双分区OTA升级、CRC32固件完整性校验、断电回滚保护、看门狗故障捕获、国产MCU硬件抽象层迁移实践。

### 覆盖能力
- Bootloader 启动流程，App 安全跳转
- A/B双分区OTA，升级断电保护，失败自动回滚
- CRC32固件完整性校验、版本元数据管理
- IWDG / WWDG看门狗，HardFault故障现场保存
- 国产MCU固件迁移，硬件抽象层适配思路

## 一、Flash分区规划设计
将MCU内部Flash划分为4个逻辑区域；若内部Flash容量不足，可外接SPI‑Flash存放升级镜像。

| 分区 | 作用 | 说明 |
| ---- | ---- | ---- |
| Bootloader区 | 上电第一执行，校验固件、升级逻辑、App跳转 | 固定起始地址，做写保护，防止误擦除 |
| Slot‑A(Active) | 当前正在运行的业务App | 正常工作运行区 |
| Slot‑B(Update) | OTA下载的待升级固件分区 | 升级时写入，不破坏正在运行的Slot‑A |
| Meta元数据扇区 | 存储升级标志、CRC32校验值、版本号、重试计数 | 独立扇区，存放升级状态，原子写入 |

> 💡 核心思想：**永远不覆盖正在运行的固件**，新版本写入备用Slot‑B，全部校验通过之后才切换启动分区；升级失败直接回退到老版本，避免设备变砖。

### Meta元数据结构体示例
```c
typedef struct{
    uint32_t magic;         // 魔术字 0xA5A5A5A5
    uint32_t crc32_slotA;   // A区固件CRC32
    uint32_t crc32_slotB;   // B区固件CRC32
    uint8_t boot_select;    // 0:启动A，1:启动B
    uint8_t update_state;   // 0:空闲，1:正在升级，2:升级完成待验证
    uint8_t retry_cnt;      // 启动重试次数，超过阈值回滚
    char version[16];       // 固件版本字符串
} ota_meta_t;
```

> 
> 📌 Meta 扇区写入遵守原则：**先修改元数据状态，再写入固件镜像；固件全部写完，再修改 boot_select 启动标记**，保证断电后状态可恢复。

## 二、Bootloader 工作流程

上电后 MCU 硬件从`0x08000000`启动，首先执行 Bootloader 代码。

1. Bootloader 初始化基础外设（时钟、串口、IWDG 看门狗提前开启）
2. 读取 Meta 元数据扇区，校验 magic 魔术字合法性；魔术字错误判定元数据损坏，直接启动 Slot‑A。
3. 根据`boot_select`选择待启动 Slot，对目标 Slot 固件执行 CRC32 完整性校验。
   - 校验失败：重试计数`retry_cnt++`；重试超过最大次数，强制回滚到另外一个可用 Slot。
   - 校验成功：复位重试计数。
4. 校验通过，重定向向量表 `SCB‑>VTOR`，关闭中断，跳转到 App 复位入口地址。
5. 如果元数据标记`update_state=1`，进入 OTA 数据接收流程，接收分段固件包写入 Slot‑B。

> 
> ⚠️ 关键踩坑
> 
> 
> 1. Bootloader 跳转 App 前，必须关闭全部外设、关闭中断，防止残留中断向量导致 HardFault。
> 2. App 链接脚本的起始地址必须对应 Slot‑A / Slot‑B 偏移，向量表偏移配置不能写错。

## 三、OTA 升级完整业务流程

1. **业务 App 阶段**：收到上位机 / 蓝牙 OTA 升级指令；停止非实时任务，保存用户配置参数；设置 Meta 元数据`update_state=1`，写入 Flash；软件复位，进入 Bootloader。
2. **Bootloader 接收固件**：分段接收 bin 固件包，逐段写入 Slot‑B 分区，每写入一块做 CRC 增量计算。
3. **全部接收完成**：计算 Slot‑B 完整 CRC32，写入 Meta；设置`update_state=2`（待验证）；软件复位。
4. **第一次启动新版本**：Bootloader 校验 Slot‑B CRC 合法，启动 Slot‑B 新固件。
5. **业务 App 自检确认**：新 App 运行完成基础自检（时钟、外设、参数加载正常），主动修改 Meta 标记确认升级成功，清除重试计数。
6. **升级失败场景**：新固件上电崩溃、看门狗复位，`retry_cnt`不断累加；达到阈值，Bootloader 检测到多次启动失败，自动修改`boot_select`切回旧 Slot‑A，实现断电回滚。

### 升级异常场景覆盖

- 下载中途断电：Meta 保留`update_state=1`标记，下次上电 Bootloader 识别，可支持断点续传或者直接放弃本次升级。
- 固件传输错误：CRC 校验直接拦截，拒绝启动损坏镜像。
- 新版本固件 Bug 反复崩溃：依靠重试计数自动回退到老版本，设备不会变砖。

## 四、固件可靠性基础模块

### 4.1 看门狗系统 IWDG + WWDG

- **独立看门狗 IWDG**：LSI 独立内部 RC 时钟，即使主时钟崩溃依旧工作；在 Bootloader 最早期就开启，防止死循环、时钟失效锁死。
- **窗口看门狗 WWDG**：不仅检测长时间不喂狗；还检测喂狗过早，捕获程序卡在高频死循环的异常；可开启 EWI 早期唤醒中断，复位前保存故障现场。

> 
> ❗ 量产禁忌：不要在中断函数内喂狗；喂狗逻辑放在主循环；高优先级任务不能长时间阻塞主循环，否则看门狗误复位。

### 4.2 HardFault 故障现场保存

发生硬件异常时，把栈帧 `PC`、`LR`、`CFSR`故障寄存器存入 RTC 备份寄存器或者 Flash 备份扇区；下次上电通过串口导出故障信息，用于定位现场死机问题，而不是直接无声复位。

> 
> 💡 调试版本打印故障信息；量产版本可把故障日志存储非易失区，便于售后分析。

### 4.3 Flash 操作注意事项

1. Flash 扇区擦写有寿命，元数据扇区做写次数限流，不要高频反复擦写。
2. 升级、写参数时关闭全局中断，防止擦写 Flash 期间中断触发引发异常。
3. 重要配置数据增加备份扇区，单扇区损坏可以读取备份。

## 五、国产化 MCU 迁移适配实践

当从 STM32 迁移到 GD32、APM32 等国产 Cortex‑M MCU，**引脚 pin‑to‑pin 兼容不等于外设行为完全兼容**。

### 迁移踩坑清单

1. **时钟树**：PLL 倍频、Flash 等待周期、AHB/APB 预分频必须重新计算；部分国产 MCU 最大主频与 ST 原厂不同，直接沿用旧配置会造成时序异常。
2. **外设寄存器差异**
   - USART：标志位名称、波特率误差存在差异
   - DMA：流与通道映射关系变化
   - TIM 定时器：预分频、死区刹车寄存器细节不同
   - I2C：时序参数需要微调，容易出现通信不稳定
3. **启动文件 & 链接脚本**：替换 startup 启动汇编，修改 Flash、SRAM 地址；Bootloader 项目重点核对中断向量表偏移 VTOR 配置，极易引发跳转 HardFault。
4. **看门狗参数**：预分频、窗口时间参数和 ST 不完全一致，不能直接复制旧的超时配置。

### 推荐架构：硬件抽象层 HAL 分离

把厂商底层驱动隔离在`platform`文件夹，业务应用层调用统一抽象接口，不直接调用芯片厂商 HAL 库函数。业务逻辑完全不感知底层是 STM32 还是国产 MCU，降低后续替换成本。

```
firmware/
├── app/          # 业务逻辑，不直接操作寄存器
└── platform/     # BSP底层适配层
    ├── stm32/
    └── gd32/
```

## 六、实测踩坑记录

1. **OTA 升级后偶发 HardFault**
   - 现象：升级后偶现跳转 App 直接死机。
   - 根因：Bootloader 跳转 App 的时候部分外设时钟未关闭，残留中断挂起。
   - 解决：跳转前关闭所有外设时钟，关闭 NVIC 全部中断。
2. **CRC 校验正常，但升级后设备随机崩溃**
   - 现象：整体 CRC 正确，但个别 Flash 位翻转。
   - 解决：除完整镜像 CRC，关键配置元数据增加单独校验；增加启动自检，关键寄存器读回二次核对。
3. **国产替换后串口通信乱码**
   - 现象：同样波特率配置，STM32 正常，GD32 出现乱码。
   - 根因：内部 RC 时钟精度差异，波特率分频计算不一致。
   - 解决：使用外部晶振，重新计算波特率分频参数。
4. **看门狗误复位**
   - 现象：业务逻辑正常，不定时看门狗复位。
   - 根因：大数组`memcpy`、Flash 擦除耗时阻塞主循环，超过 IWDG 超时窗口。
   - 解决：拆分耗时操作，分段喂狗；合理配置看门狗超时时间。

## 七、总结

量产固件和实验室 Demo 最大区别就是面向各种异常：断电、死机、升级失败、芯片替换。

- A/B 双分区 OTA 核心价值：**永远保留一份可用固件，依靠 CRC 校验 + 重试计数实现自动回滚，解决升级变砖风险**。
- Bootloader 不只是下载器，是整个系统的安全门卫，完成固件校验、故障判断、启动决策。
- 看门狗 + HardFault 现场保存，把 “无声死机” 变成可复现、可分析故障日志。
- 硬件抽象层隔离 BSP，面对国产 MCU 替代时，减少业务层大规模改动。
