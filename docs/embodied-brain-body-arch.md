# 大脑—小脑异构架构：50 Hz 决策与 20 kHz 电流环之间

> 📄 文档路径：`docs/embodied-brain-body-arch.md`

> ✍️ 具身智能平台的第一性问题不是"策略多强"，而是**两个数量级不同的时间尺度怎么接**。本文拆这个接口：延迟预算怎么分、插值层放在哪、安全边界为什么必须在实时域闭合、延迟怎么打点测量。

> ⚠️ **文档定位**：目标平台为 **Rock 5B（RK3588）+ Unitree Qmini 双足**（开源项目：[unitreerobotics/Qmini](https://github.com/unitreerobotics/Qmini)、[vsislab/RoboTamer4Qmini](https://github.com/vsislab/RoboTamer4Qmini)）。**硬件尚未采购**，本文是架构推演与指标定义，所有性能数字均为**目标值**，未上机验证。方案背景见[具身智能边缘计算平台](../personal_project/00_embodied_ai_platform)。

## 一、先把时间尺度摆出来

具身智能系统里同时存在四种节拍，跨度接近四个数量级：

| 层级 | 典型频率 | 周期 | 跑在哪 | 失效后果 |
|---|---|---|---|---|
| 策略训练 | 离线 | 小时～天 | GPU 服务器 / Isaac Gym | 不影响运行 |
| 策略推理（决策） | 50 Hz | 20 ms | Rock 5B · Linux（非实时） | 抖动 → 动作不平滑 |
| 指令插值 / 逆解 | 200～1000 Hz | 1～5 ms | Rock 5B 或 MCU | 阶跃 → 冲击 |
| 关节电流环 | 20 kHz | 50 µs | MCU（实时） | 超时 → 失控 |

一张图能说清问题所在：

```text
20 ms ────────────────────────────────────────────────┐
      │ 策略输出一次目标                                │
      ├── 50 µs ─┬─ 50 µs ─┬─ 50 µs ─┬─ … 400 拍 ──────┤
      │  电流环  │  电流环  │  电流环  │                │
      └──────────┴──────────┴──────────┴────────────────┘
```

一次决策跨过了 **400 个电流环周期**。如果把这 20 ms 的目标**阶跃**地砸进电流环，等于每 20 ms 给关节一次冲击激励 —— 电流尖峰、机械冲击、噪声全在这里产生。

所以两端之间必须有一层**把阶跃变成连续可导轨迹**的东西。这层的存在，才是"异构"三个字的实际含义。

## 二、延迟预算：先分配，再实现

不分配预算就调不动。按 50 Hz 闭环倒推，20 ms 一拍里各段能占多少：

| 环节 | 目标预算 | 说明 | 测量手段 |
|---|---|---|---|
| 传感器采集与同步 | ≤ 2 ms | 相机曝光/传输占大头，IMU 可忽略 | 时间戳对比 |
| 状态估计 | ≤ 1 ms | IMU + 关节反馈融合 | 函数入口/出口打点 |
| 策略推理（NPU） | ≤ 3 ms | MLP 级策略，INT8 | `rknn_query` 性能接口 |
| 推理前后处理 | ≤ 2 ms | 归一化、拼观测向量 | 同上 |
| 传输（大脑→小脑） | ≤ 1 ms（p99） | 以太网 / CAN FD | 收发时间戳差 |
| 插值与限幅 | ≤ 0.2 ms | MCU 侧，随电流环跑 | GPIO 翻转 + 示波器 |
| **余量** | **≈ 10 ms** | 留给抖动、重传、调度毛刺 | — |

三点说明：

1. **余量必须留一半**。Linux 侧调度抖动不是正态分布，是长尾。按平均值做预算，实机必然偶发超时。
2. **p99 比均值重要**。传输段看平均值没有意义 —— 1 ms 均值配 8 ms 尖峰的系统，跑起来就是周期性抽搐。
3. **测量口径要统一**。打点必须用同一个时钟源（建议 MCU 的 SysTick，Linux 侧用 `CLOCK_MONOTONIC` 并做偏移标定），否则算出来的延迟是假的。

## 三、为什么安全逻辑不能放在大脑

这是本文最重要的一条，也是"双域"方案唯一不可替代的理由。

把安全逻辑放在 Linux 侧，会遇到三个无法用软件工程解决的问题：

1. **调度不可界**。普通内核上，一个高优先级线程的最坏响应时间没有上界；PREEMPT_RT 只是把上界压小，不是消除。策略推理本身是计算密集的长任务，和看门狗线程抢同一个 CPU 时，看门狗的延迟取决于调度器的运气。
2. **内存与驱动故障不可隔离**。NPU 驱动、相机驱动、DMA 缓冲区，任何一处出问题都可能让整个用户态卡住 —— 而卡住的时候恰恰最需要安全动作。
3. **崩溃恢复时间不可控**。进程重启、服务拉起，秒级起步。而机器人倒地只需要几百毫秒。

所以安全逻辑必须满足两个条件：**跑在实时域内**、**不依赖上层存活**。具体到实现，MCU 侧至少要独立完成：

| 安全动作 | 触发条件 | 响应时间目标 |
|---|---|---|
| 关节目标限幅 | 单拍增量超阈值 | 立即（本周期内） |
| 通信超时降级 | 连续 N 拍未收到指令 | ≤ 50 ms |
| 平滑收腿 | 收到降级信号 / 姿态超限 | ≤ 500 ms 完成 |
| 断电抱闸 / 阻尼模式 | 电压跌落 / 严重故障 | ≤ 20 ms |

注意"平滑收腿"这个设计要求：直接切断 PWM 会让双足机器人像一袋零件一样倒下。收腿是一条**受控轨迹**，需要梯形速度规划 + 关节限幅，最后才进入阻尼或抱闸。

## 四、插值层：把 20 ms 的阶跃变成连续轨迹

三个可选位置，各有取舍：

| 位置 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| 大脑（Linux） | 策略输出后立刻插值成 1 kHz 序列 | MCU 只做透传，逻辑集中在 Linux | 传输量 ×20；Linux 抖动直接进入指令序列 |
| **小脑（MCU）** | 收到 50 Hz 目标 + 时间戳，本地插值 | 抖动被本地时钟吸收；传输量小 | MCU 要算插值，占 CPU |
| 硬件（FPGA/专用） | — | 确定性最好 | 成本与复杂度不匹配 |

**推荐小脑侧**，理由：插值本质是"用本地时钟重建连续运动"，而本地时钟在实时域里才有意义。放在 Linux 侧插值，等于让抖动先污染数据、再试图用算法修复。

插值函数的选择：

- **线性插值**：简单，但速度不连续 —— 加速度是冲激，电流环会看见阶跃。
- **三次多项式**：速度连续，加速度仍跳变。
- **五次多项式**：位置、速度、加速度全部连续，起止点约束可设为 0 —— 这是四足/双足步态里常用的选择。
- **临界阻尼二阶滤波**：实现最省，`y[n] = y[n-1] + k·(target - y[n-1])` 的连续化形式，参数物理意义清晰（自然频率 ωn、阻尼比 ζ=1），适合"目标持续刷新"的场景。

工程上常用组合：**五次多项式做段间过渡，临界阻尼滤波做在线跟踪**。前者处理"从 A 到 B"，后者处理"目标一直在变"。

## 五、延迟可测量：不打点就没法调

延迟优化的前提是能测。分三段打点：

```text
[T1] 传感器采样完成 ──► [T2] 推理开始 ──► [T3] 推理结束
                                              │
                                              ▼
[T4] 指令发出 ──► [T5] MCU 收到 ──► [T6] 电流环生效
```

- **T1–T2**：前处理开销；
- **T2–T3**：NPU 推理（用 `rknn_query` 拿硬件侧计时，比用户态前后差值准）；
- **T3–T4**：后处理 + 序列化；
- **T4–T5**：链路时延（两端时钟需标定偏移，用最小二乘拟合单向延迟）；
- **T5–T6**：MCU 队列排队 + 插值，用 GPIO 翻转 + 逻辑分析仪测，微秒级精度。

一个实用技巧：**在指令帧里带发送时间戳，MCU 收到时算出单向延迟并回传**，形成一个持续的延迟监控通道。这样不用外接仪器就能在运行时观察 p99。

## 六、Rock 5B + Qmini 的具体映射

| 层 | 本方案 | Qmini 原版 | 差异动机 |
|---|---|---|---|
| 大脑 | Rock 5B（RK3588，6 TOPS NPU） | 树莓派 4B | 需要 NPU 跑策略；树莓派纯 CPU 推理 MLP 尚可，稍大的网络就掉帧 |
| 小脑 | Qmini 自带主控 / 外挂 MCU | 树莓派直接驱电机 | 把安全逻辑从非实时域拿下来 |
| 链路 | 以太网 / USB-485 | USB-485 | 取决于 Qmini 是否开放 CAN/EtherCAT |

> ⚠️ 一个待确认项：Qmini 的关节电机走 Unitree 自家协议（物理层 RS485，官方 BOM 配 USB-485 适配器），**是否开放底层控制接口、能否绕过原厂主控直连**，需要在采购前确认。若不开放，P1 之后的验证要改用自建四足平台（复用 01 项目的 CAN 主控）。这条不确认就下单，风险不小。

## 七、这套架构的失败模式

提前写下来，省得踩了才想起来：

| 失败模式 | 表现 | 根因 | 对策 |
|---|---|---|---|
| 抖动传导 | 机器人规律性抽搐，周期约 20 ms | 插值层缺失或插值在 Linux 侧 | 插值下沉到 MCU |
| 长尾超时 | 偶发（几分钟一次）大幅动作 | Linux 调度毛刺 + 无余量 | 预算留 50% 余量；`isolcpus` + 线程亲和 |
| 时钟漂移 | 运行越久动作越"拖" | 双端时钟未标定 | 定期重标定偏移 |
| 收腿失败 | 断链后机器人直接倒 | 安全逻辑在 Linux 侧 | 安全逻辑下沉 MCU |
| 推理掉帧但无感知 | 策略输出重复上拍的值 | 无心跳/序号校验 | 指令帧加序号，MCU 检测连续性 |
